The problem

Most engineering tasks take longer than one Copilot conversation. You investigate in the morning, implement after lunch, pass the work to a teammate, and someone else reviews it next week. Each of those is a separate session. When a session ends, so does everything you established in it: what you checked, which source you trusted, and what was decided.

What changes in how you work

The practical difference on the Monday after, written as behaviour rather than concepts.

Today After this lab
You attach every file that might be relevant and trust the model to work out which one is current. You decide what gets in, and you can say which source is allowed to settle which kind of claim.
You paste raw build output into chat, spending hundreds of lines to learn one fact. A skill runs the command and hands back six lines. It reports a failure if the build never ran, rather than a clean summary.
What you worked out lives in scrollback and disappears when the tab closes. What you verified is written down with its source, and the next session starts from it.
"Do not touch that config" is written into a prompt and hoped for. The role does not have that tool at all, so no phrasing can get it back.
You confirm the acceptance criteria by reading the code and agreeing it looks right. The criterion that must never regress runs as a check that executes the method and compares the number.
Handing work over means forwarding the conversation and hoping it gets read. Handing over means passing the decision and the evidence for it, without the discussion that produced it.

How this differs from Part 1

The two labs cover different halves of the same problem. Part 2 assumes the four levers from Part 1 and does not repeat them.

Part 1 — inside the session

Make one conversation cheap and accurate.

  • Target: attach the right file and the right selection
  • Reuse: prompt caching and cache hygiene
  • Isolate: clear a stale session between tasks
  • Match: size the request to the task
Part 2 — across the breaks

Make the work survive when no single conversation can hold it.

  • Evidence and authority: which source settles which kind of claim
  • Durable facts: recorded with their source, not remembered
  • Isolation: each role works in its own context window
  • Enforcement: checks that run outside the model
  • Rehydration: rebuilding the task from files alone

Part 1 measures the cost of a request. Part 2 measures the cost of a restart.

Three ways to enforce a rule

A rule written into a prompt is the weakest of the three. The second half of the lab is spent on the two stronger ones, and the difference between them explains most of the design decisions in the stages that follow.

The Copilot features you use

The lab is built on GitHub Copilot customization features. Each one is defined in the repository, versioned with it, and invoked from chat. You use all six across the eight stages, and in the final stage you build one of your own.

Primitive What it is Where you meet it
.github/skills/
Skill		 Wraps a command and returns only its summary, never the raw output. Used from Stage 1 onward. You build your own in Stage 7.
.github/prompts/
Prompt file		 A reusable instruction with no command behind it. It standardises the wording, not the result. Formats your register in Stage 3. Generates your kit in Stage 7.
.github/agents/
Custom agent		 A role holding a restricted toolset, so it cannot exceed its remit even when asked to. Stage 4 — an investigator that cannot edit, an implementer that reads only the handoff.
agents:
Subagent		 An agent called by another agent. It works in its own window and returns an answer, so the caller never sees the work behind it. Stage 4, where the investigator calls evidence-checker rather than reading files itself, and Stages 3 and 6, where a harness runs one question against two different contexts.
.github/hooks/
Hook		 Runs automatically when something happens, and can block an action rather than advise against it. Stage 5 — the bound on the repair loop.
AGENTS.md
Instructions		 Standing rules that apply to every request without being attached to any of them. Throughout, shaping how Copilot answers questions about the codebase.

The hard part is not writing any one of these. It is knowing which one a job needs.

Stage 4 works through that judgment directly, and the answer is not to delegate everything. Two of the roles in this lab are deliberately not subagents:

Role Built as Because
Evidence checkerSubagentA narrow question that takes noisy work to answer. The caller needs the answer, not the work.
ImplementerGated handoffCalling it as a subagent would let the investigator decide on its own that it is time to build. A person approves that step.
ReviewerFresh invocationA subagent gets a clean window, but the agent calling it still writes the question. Isolation is not the same as independence.
Digest toolsSkillAlready the right fit. Making them agents would add ceremony without adding capability.

Stage 7 asks you to make the same call on something you built yourself: whether it belongs as a skill, a prompt file, a hook, a CI check, or nothing at all, since building infrastructure for a question you will only ask once is wasted effort.

None of this layer is specific to Java. The scenario uses a Java service, but .github/skills/, .github/prompts/ and .github/agents/ work the same way in a .NET, Python or TypeScript repository. That is why the toolkit you generate in Stage 7 goes into your own codebase rather than this one.

How the session runs

The whole session runs on one ticket: adding a real-time payment fee to a payments service. Two sources in the repository state different rates, and nothing on record says which one is current. Eight stages, grouped into four parts.

Movement 1

See the problem

7 min

You attempt the ticket first, before anyone offers a technique.

0The Helpful Trap7 min

You leave able toExplain why the problem is unsorted context rather than missing context, and why adding more context does not reliably help.

You give Copilot the ticket the way you normally would, then check which claims in its answer are backed by evidence and which only sound right.

UsesPlain chat only. No skills, no agents, by design.

Movement 2

Build the discipline

39 min

Three habits, each replacing a reflex: check before you retrieve, compute before you paste, record before you move on.

1Discover Before You Retrieve10 min

You leave able toWork out what kind of claim you are making before choosing a tool, and say which kind of evidence can settle it, including when the answer is that no tool can and a person has to decide.

A routing table shows which files hold the answer without opening any of them. A text search then reports a dependency the compiler says is not there, and following it would have pulled an unused class with an outdated rate into the conversation.

UsesSkills: /context-map, /authority, /test-gap, /outline

2Compress Before Context10 min

You leave able toWrite the specification for a tool that summarises any noisy command in your own toolchain, and recognise the bug that makes a tidy summary more dangerous than raw output.

Raw test output compared against a six-line summary, followed by a harder question: what would that summary say if the build never ran?

UsesSkill: /context-run

3Promote & Package19 min

You leave able toShow whether the work changed an answer, by asking one question twice: once with every source attached, once with only the material you selected.

If the crowded version happened to be right, what in it would have told you so beforehand? Nothing in that context ranks its own sources, so a correct answer there is not one you could have checked.

UsesPrompt file: /promote-facts · Skill: /context-package · Subagents: Context Experiment and context-probe

Movement 3

Hold it under pressure

28 min

The work now involves other roles, and a decision the model should not make alone.

4Boundaries & Handoff14 min

You leave able toGive each role its own context window, decide which work to delegate, and recognise agreement-seeking behaviour as something caused by context rather than a flaw in the model.

The investigator dispatches a subagent to settle a claim: the compile log and file reads stay in the subagent's window, only a verdict returns. It surfaces the conflicting rates and stops. You then assert the wrong rate on purpose and watch whether it defers to you or holds its evidence. A person resolves it for real, records who decided, and only that crosses to the implementer.

UsesCustom agents: RTP Investigator, RTP Implementer · Subagent: evidence-checker

5Challenge & Bound14 min

You leave able toTurn a requirement that must not regress into a check that runs, and put a limit on a repair loop so a stuck agent escalates instead of retrying.

The seeded bug states the rule correctly in a comment while comparing the wrong operand in the code. A reviewer may catch it. The deterministic check always does. The reviewer is started fresh rather than called by the implementer, because a clean window does not help if the agent calling it still writes the question.

UsesSkill: /verify-change · Hook: the loop bound

Movement 4

Prove it transfers

44 min

Whether any of this holds up in your own codebase.

6Rehydrate & Prove9 min

You leave able toMeasure what starting over costs, and identify what a new session cannot recover however much of the repository it can read.

One new session is given three files. Another is given the whole repository and no files. Compare what each costs, then compare whether either knows that a person already settled the disagreement.

UsesSkill: /context-package in a session with no history · Subagents: the same comparison harness

7Build Beyond the Harness35 min

You leave able toBuild the missing piece yourself, and leave with working tooling installed in a codebase this lab has never seen.

A defect none of the lab tools were built to find. Then a summarising tool that you specify before prompting, build as a Copilot skill, and deliberately break to confirm it reports failure. Finally you generate the toolkit for your own repository.

UsesYou build a skill · Prompt file: /context-kit

What the stages produce

The stages are not eight separate exercises. Each one produces files that later stages read. The context register is written once and then read by three different roles, one of which has no memory of the conversation that produced it.

The ten questions you take with you

These apply to any language and any toolchain. The scripts in the lab repository are one worked example, written specifically for this scenario so there is something concrete to take apart.

What you take home

Three things go home with you. The scenario scripts are not among them; they were the worked example.

  • The ten questions. The part of the lab most likely to still apply in two years, whatever language, toolchain, or assistant you are using.
  • A kit generator. One file that you copy into any repository. It reads that repository's build file and layout, then generates the routing table, the evidence check, the test summary and the file outliner for that stack. You run it against your own code in Stage 7, so you have seen it work before you leave.
  • The tool you built yourself, available in your editor as a slash command rather than a script someone has to remember exists.
